## Platform

web

## Users

The primary user is a person handing a secret to someone else without creating an account. The secret is a password, a private note, or a developer credential such as an API key or `.env` file. They are at a browser, often on a short deadline, and they need a link the other person can open.

The recipient is the other half of that job. They have the link. A Secure Note opens from that link when the key is in the URL fragment (`#k=`), or they type a password that arrived separately, or both. An EnvShare link carries the key in the fragment. A file drop link does the same for files. They decrypt in their own browser.

The direction can also flip: with a Secret request, the person who needs the secret sends a link, and the sender's reply is encrypted to the requester's public key.

More tools sit on the same promise. Someone can keep an encrypted notepad in the browser, and optionally sync the ciphertext. Someone can open an encrypted chat room and talk with people who have the invite link or room password. The sender can check "My links" on the device that created a share to see whether it was opened, revoke it, or ask for a browser notification (Web Push) when it is opened. With the app installed, someone can share text or files into ProtectedShare from another app; they stay on the device until sealed. A recipient can report a link as abusive. The free tools (password generator, offline text encryptor, secret key generator, password strength checker, JWT decoder, Wi-Fi QR code generator) send nothing to the server; the breached password checker sends only a 5-character SHA-1 prefix, to Have I Been Pwned. Someone can also create, check and revoke links from Claude or another MCP client, through a remote connector or a local server (see the MCP line under Capabilities). An operator can self-host the web app and the API. An organization can ask, through the contact form, about a dedicated instance. That ask is not a checkout.

## Product Purpose

ProtectedShare lets someone encrypt a secret in the browser and leave only ciphertext on the server, then give another person a way to decrypt it. Success is the recipient reading the secret in their browser while the hosted database does not hold the plaintext.

The public site is [protectedshare.me](https://protectedshare.me). The repository is [github.com/KunalSiyag/protectedshare](https://github.com/KunalSiyag/protectedshare), MIT licensed.

## Positioning

The mechanism is client-side AES-256-GCM (crypto v2, `packages/crypto/src/v2.ts`). The input is a random 32-byte key carried in the URL fragment, or a password stretched with PBKDF2-SHA256 at 600,000 iterations, or both. HKDF-SHA256 derives two values from it: the AES-256-GCM key and an auth token. The server stores the ciphertext, IV, salt, KDF mode and SHA-256 of the auth token, and releases ciphertext only to a client that presents the token. It does not store the key, the password or the plaintext. Legacy v1 links (PBKDF2 210,000 iterations plus a fixed-salt password proof) still open.

A Secure Note can keep the password off the link, for a second channel, or place the key in the fragment so the link opens the note. EnvShare puts the key in the fragment, which the browser does not send to the server, and deletes the row after a chosen number of reads. File drop encrypts files in chunks bound to their position. Secret requests use ECDH P-256 so only the requester's private key opens the reply. The encrypted notepad and the chat room use the same browser encryption for contents that live longer than a single link.

That combination is the position: one open-source web app for an account-free handoff (text, credentials, files, or a request in the other direction), a private notepad, and an encrypted chat room. Comparison pages against EnvShare, Privnote, ProtectedText, and OneTimeSecret are marketing pages in the app. They are not an audit of those products.

## Operating Context

A sender opens Secure Notes, EnvShare or File drop, adds the secret, sets an expiry, and encrypts it locally. Expiry is 1 hour, 1 day, 7 days, or a custom date at most 30 days out. Notes can burn after the first open. EnvShare allows 1 to 100 reads. File drops take up to 25 MB and 1 to 100 downloads. The sender copies a link (or shows a QR code). A note link can include the key, or a password can be sent separately. The share is saved to "My links" in that browser with a manage token.

The recipient opens the link. The page reads the key from the fragment when present, otherwise they type the password. Decryption runs locally. Burn-after-read, a spent read or download count, revoke, and expiry delete the database row. A cron every 30 minutes deletes expired rows; reads past expiry are refused before that.

The notepad is a markdown scratchpad. Local mode keeps the vault in the browser. Cloud mode uploads ciphertext and merges conflicting saves with the server's `updated_at` version (HTTP 409, then a client-side merge). A note can also be downloaded as a self-decrypting HTML file that opens offline.

Chat creates a room with a random key in the invite link (`#r=…&k=…`), or a password. The room is claimed with an auth hash so only members can read or post. Messages are ciphertext and can carry a disappearing timer; images and files travel inside the ciphertext. Members compare safety words derived from the key. Presence (a random client id and a typing flag) is separate from message contents. Messages are purged when everyone leaves; anyone in the room can burn it.

Self-hosting is a Cloudflare Worker with D1 for the API (with a `*/30 * * * *` cleanup cron in `wrangler.toml`), an R2 bucket `protectedshare-drops` for file-drop chunks (it must exist before deploying; deleting the `[[r2_buckets]]` block keeps chunks in D1), and the Next.js app pointed at it with `API_BACKEND_URL`. The README and `/self-host` describe Wrangler, the schema and migrations 0001–0008 (the Worker also self-heals missing tables and columns), the optional rate limiters (namespace ids 71001–71006, unique per account), the optional secrets (`RESEND_API_KEY`, `ADMIN_TOKEN` of at least 32 characters, `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`/`VAPID_SUBJECT` from `npm run vapid:generate -w @protectedshare/api`), the optional email settings `NOTIFY_EMAIL_TO` (default admin@protectedshare.me) and `NOTIFY_EMAIL_DOMAIN` (default protectedshare.me, which must be a domain verified in Resend), the build-time web settings (`NEXT_PUBLIC_GA_ID`, `NEXT_PUBLIC_CF_BEACON_TOKEN`, `NEXT_PUBLIC_VAPID_PUBLIC_KEY`, `NEXT_PUBLIC_GOOGLE_SITE_VERIFICATION`), a container image at `ghcr.io/kunalsiyag/protectedshare-web` (built with none of those settings), and optional GitHub Actions deploy. The hosted site's `vercel.json` rewrites `/api` straight to the API Worker; self-hosters using the built-in `/api` proxy send every request from one IP, so `RL_CREATE` becomes a site-wide cap. The optional remote MCP server is a second Worker (`apps/mcp`, deployed with `npx wrangler deploy`; self-hosters delete its `mcp.protectedshare.me` custom-domain route, set `SITE_URL`, and keep the `protectedshare-api` Service Binding or set `API_BASE_URL`). Local development is `npm run dev:api` and `npm run dev:web` from the repo root (plus `npm run dev:mcp` for the MCP server): web on port 3000, API on port 8787, MCP on port 8790. Without `API_BACKEND_URL` the web proxy falls back to the hosted API.

## Capabilities and Constraints

Confirmed behavior:

- Secure Notes, EnvShare secrets, file drops, secret requests, notepad vaults, chat messages, the offline HTML export and the encrypt-text tool encrypt with AES-256-GCM in the browser (`packages/crypto`).
- v2 retrieval (notes, secrets, drops) sends an auth token derived by HKDF from the key or password in header `X-Auth-Token`; the server stores and compares SHA-256 of it in constant time. The token is a verifier, not the decryption key, and it does leave the browser.
- Legacy v1 notes and secrets, and notepad workspaces, send a password proof: PBKDF2 at 100,000 iterations with the fixed salt `protectedshare-proof-salt-v1`, then SHA-256. Older workspaces can still authenticate with a legacy SHA-256 of the password and are migrated forward.
- Secret requests: ECDH P-256 + HKDF-SHA256 + AES-256-GCM. The server stores the requester's public key, an encrypted label (always sent; it carries a SHA-256 fingerprint of the public key that the sender's browser checks before sending), a hash of the respond token (HKDF of the sender link's `#k=`, required in `X-Auth-Token` to reply), a hash of the inbox token, and the encrypted reply until the inbox collects it (then deletes the row).
- File drops: chunks up to ~1 MB, each AES-256-GCM with its index and count as AAD; the manifest (names, types, sizes) is encrypted. Chunk bytes are stored in R2 under `drops/<id>/<idx>` when the `DROPS_BUCKET` binding exists (`apps/api/src/lib/drop-storage.ts`); D1 keeps one row per chunk with its size, and without the binding the bytes stay in D1. The server sees total encrypted size, chunk sizes, chunk count, downloads remaining and expiry. A download is counted by the server when it starts (atomic decrement plus a 60-minute download session whose token every chunk request needs); cancelling doesn't refund it, and the receipt marks the drop opened at that point. Unfinished uploads are purged after 6 hours. R2 objects are deleted with the drop (last download, revoke, admin takedown, cron), and the cron sweeps orphaned objects, scanning only the first ~10,000 drop prefixes per run, so a bucket lifecycle rule is recommended as a backstop.
- Receipts: when a share is created with a manage token, the server stores SHA-256 of the token and a receipt row (kind, id, status, reads, max reads, created/expiry/first-read/last-read times), never content, kept until 30 days after expiry. "My links" (`localStorage` key `ps.links.v1`, this browser only) reads receipts in batch, can revoke, and can switch read notifications on or off; the manage token leaves the browser only for those calls.
- Read notifications (`apps/api/src/routes/notify.ts`, `src/lib/webpush.ts`, migration `0008_push.sql`, `apps/web/lib/push.ts`, `apps/web/public/sw.js`): the manage-token holder registers a browser push subscription (`POST /api/manage/:kind/:id/watch`). `share_watchers` keeps, per browser and at most 5 per share, the push endpoint (allow-listed Google, Mozilla, Apple and Microsoft push services only), the subscription's `p256dh` key and auth secret, kind, id and created time: no content, key, IP or account. On the first counted open and on the read that uses the share up, the Worker sends an RFC 8291-encrypted payload `{ kind, id, event, at }` padded to 128 bytes, TTL one day, with an RFC 8292 VAPID token; the push service learns that and when a message was sent, not its content. Rows are deleted after the used-up push, on revoke or takedown and when the receipt is deleted (triggers), on 404/410 from the push service, and by the cron once the share is no longer active. The browser keeps IndexedDB `ps-notify` (kind, id, local label, expiry; never the URL, key or manage token) and a service worker scoped to `/share-target/` that caches nothing, registered only when the user turns notifications on or by the installed app (`components/standalone-sw.tsx`); other pages only look up an existing registration. Off unless `VAPID_*` Worker secrets and `NEXT_PUBLIC_VAPID_PUBLIC_KEY` are set.
- Share target (`apps/web/app/manifest.ts`, `apps/web/app/share-target/**`, `public/sw.js`): in the installed app, shared text and files are taken by the service worker into IndexedDB `ps-share-inbox` on the device. Any website can also POST to `/share-target/receive`, so `/share-target` first shows what arrived ("This arrived from another app or website. Check it before you seal anything.") and moves on only on a click: text alone is cleared as soon as the page reads it; files stay until the user continues to File drop, which takes only an item that click approved, or discards them; items older than 15 minutes are discarded unread. If the worker isn't running yet, the `POST` reaches the web host's `/share-target/receive`, which redirects without reading or logging the body; in the installed app the page then registers the worker and says so, and a browser tab gets no worker. `components/standalone-sw.tsx` registers the worker on the installed app's first launch.
- Rate limits (`apps/api/src/lib/limits.ts`, `[[ratelimits]]` in `wrangler.toml`, all optional, counted per Cloudflare location so approximate): `RL_AUTH` 10 wrong keys or passwords a minute per share, room or notepad; `RL_CLAIM` 30 joins a minute per room; `RL_RESPOND` 10 answers a minute per request; `RL_CHAT_POST` 120 messages a minute per room; `RL_REPORT` 5 reports a minute per reported link (and 5 report emails a minute per Cloudflare location); `RL_CREATE` 600 creates a minute per client IP (`CF-Connecting-IP`, IPv6 grouped by /64), passed to the limiter only and never written to D1. Behind the hosted site's Vercel rewrite that IP is a Vercel egress address shared by many visitors, so one client that reaches the limit holds up creates for the others on it for the rest of the minute. Past `RL_AUTH`, password-protected targets (v1 links, password and key+password notes and secrets, chat rooms, notepads) lock for 10 minutes; `auth_lockouts` stores only `auth:<scope>:<id>` and the end time, and while locked every attempt is refused. Key-only links, drops and requests never lock.
- Abuse reports (`apps/api/src/routes/reports.ts`, `apps/web/components/report-abuse.tsx`): recipient pages for notes, secrets, drops and requests post kind, id, reason, optional details (≤500 characters) and optional contact email to `abuse_reports`, kept 180 days; text containing a link key is refused by the form and the server. With `RESEND_API_KEY`, an HTML-escaped email goes through Resend to `NOTIFY_EMAIL_TO` (default admin@protectedshare.me). `DELETE /api/admin/:kind/:id` with `X-Admin-Token` (the `ADMIN_TOKEN` secret, at least 32 characters, or the route answers 404) deletes the content and R2 objects and marks an active receipt revoked.
- Usage counts (`apps/api/src/lib/usage.ts`, `GET /api/stats`): `usage_daily` holds one count of successful creates per UTC day and kind (note, secret, drop, request, chat), no ids or content, kept 400 days. `/api/stats` returns 30-day totals (cached 10 minutes); the homepage shows the total only when it is at least 250 (`components/home/usage-stats.tsx`).
- MCP (`apps/mcp`, `packages/mcp-core`, `packages/mcp-server`; official MCP TypeScript SDK `@modelcontextprotocol/server` 2.3.1, pinned; MCP 2026-07-28 plus 2025-11-25, 2025-06-18 and 2025-03-26). Tools in both servers: `create_secret_link`, `share_env_file`, `request_secret`, `check_link_status` (read-only), `revoke_link` (destructive) and `generate_password` (read-only, nothing stored); the local server adds `open_secret_link` (destructive: it spends a read like a browser, and labels the returned text as written by the link's creator) and `check_password_breach` (read-only; only a 5-character SHA-1 prefix goes to `api.pwnedpasswords.com`, from the user's machine). Both create links through the same storage API with manage-token receipts, so storage is identical to the website's. Link keys, request key pairs and manage tokens are generated where the tool runs and returned in the tool result, never stored, so they (and any plaintext the user gave the assistant) are in the conversation the MCP client and its AI provider see; these links don't appear in "My links".
  - Remote connector: `https://mcp.protectedshare.me/mcp`, the Worker `protectedshare-mcp` on a Cloudflare custom domain (the web host is not in the path). Plaintext a tool receives passes through the Worker's memory over TLS; it encrypts with crypto v2 (AES-256-GCM, key-in-link only, no password modes) and sends the storage API ciphertext and hashes to create, and kind, id and manage token to check or revoke, over a Service Binding. It stores nothing; it never logs arguments, results or bodies; Workers observability records request metadata (method, path, status, timing) and a rejected request logs only an error class name. POST only, JSON responses, no sessions, 512 KB body limit, protocol-header validation, 25-second API timeouts, strict input validation (notes and EnvShare up to 50,000 characters, for the Workers CPU budget), error messages without request data. An `Origin` header, if present, must be claude.ai, claude.com or localhost (else 403). One JSON-RPC message per POST: batch arrays are refused with 400 in both eras. Optional limiters keyed on the connecting IP (IPv6 grouped by /64): `RL_MCP` 600 requests a minute, and `RL_MCP_CREATE` 120 calls a minute to `create_secret_link`, `share_env_file` and `request_secret`, counted from the parsed body (Claude's connector traffic comes from Anthropic's servers, so its users share those budgets). No accounts, cookies or OAuth.
  - Local server: `npx protectedshare-mcp` (stdio) encrypts and decrypts on the user's machine (passwords: PBKDF2-SHA256, 600,000 iterations). It sends `https://protectedshare.me/api` (through the web host to Cloudflare) ciphertext and hashes to create, the link id and a derived auth or inbox token to open, and kind, id and manage token to check or revoke; never plaintext, link keys, passwords or private keys. User-Agent `protectedshare-mcp/<version>`; the user's IP is visible to the web host and Cloudflare like any API call. It writes nothing to disk; stderr names only an error's type. Settings: `PROTECTEDSHARE_API_URL` and `PROTECTEDSHARE_HIBP_URL` (https only, except localhost).
- Chat v2: claimed rooms store an auth hash and a default disappearing timer; messages may carry an expiry and a delete-token hash. Messages are purged when no one is present (on the room's next request or by the 30-minute cron, not instantly), at their expiry, or on burn; idle room claims are forgotten after 7 days.
- Cloud notepad usernames are stored as the SHA-256 of the normalized username. Local notepad usernames are stored in the browser in normalized form; the local vault's key is stored in the same browser.
- The API is a Hono app on Cloudflare Workers with D1 tables for notes, secrets, workspaces, workspace sessions, chat messages, chat presence, chat rooms, chat deletions, drops, drop chunks, drop sessions, requests, share receipts, share watchers, auth lockouts, abuse reports, daily usage counts, and inquiries, plus an R2 bucket for file-drop chunks (`apps/api`). The Worker creates missing tables and columns at runtime (`src/lib/schema.ts`). A cron runs every 30 minutes to purge expired rows. Workers observability logs are enabled.
- The web app is Next.js 15 App Router, React 19, and Tailwind 3.4 (`apps/web`). Shared UI primitives live in `packages/ui`. Payload shapes live in `packages/contracts`.
- There is no payment flow and no public price. The homepage JSON-LD says the offer price is 0. The contact page invites organizations to ask about a dedicated instance. No price or contract for that instance is in the repo.
- The contact form stores a name, an email, an optional company, and a message in the `inquiries` table, and emails it to the admin through Resend when `RESEND_API_KEY` is set. Contact and report emails go to `NOTIFY_EMAIL_TO` (default admin@protectedshare.me) from `deals@` (contact) or `reports@` (reports) at `NOTIFY_EMAIL_DOMAIN` (default protectedshare.me; it must be verified in Resend), per `notifyEmail` in `apps/api/src/lib/env.ts`.
- The app sets no cookies of its own (no `document.cookie` or `Set-Cookie` in the code). Google Analytics sets its own cookies when enabled. The privacy page states, at build time, whether GA is on.
- Google Analytics loads only when `NEXT_PUBLIC_GA_ID` is set, and Cloudflare Web Analytics only when `NEXT_PUBLIC_CF_BEACON_TOKEN` is set (`apps/web/components/analytics.tsx`). Neither loads on share-holding paths (`/notes/[id]`, `/secrets/[id]`, `/files/[id]`, `/request/[id]` and inbox, `/chat`, `/links`, `/notepad`, `/share-target`), and each is switched off if one is visited later in the session. GA page views are sent manually with origin and path only. The Cloudflare beacon sets no cookies, drops the query and fragment from what it reports, and counts full page loads only (its SPA mode is off). The repo does not record whether the hosted site sets either.
- New note and EnvShare ids are 10 characters (v1 ids are 5). Online guessing of password-mode notes is rate limited and locked as above; each guess also costs 600,000 PBKDF2 rounds, and a copy of the database can still be guessed against offline.
- The breached password checker (`apps/web/app/tools/breached-password-checker/pwned.ts`) hashes with SHA-1 in the browser and sends only the first 5 hex characters to `api.pwnedpasswords.com/range/` with `Add-Padding: true`, no cookies and no referrer. Every other free tool makes no network request.
- `/api/*` is relayed by the web app's host to the Worker (`apps/web/app/api/[[...path]]/route.ts`, or the rewrite in `apps/web/vercel.json`), so that host sees request metadata and ciphertext as well as Cloudflare. The Next proxy route drops cookies and client forwarding headers and refuses bodies over 2,000,000 bytes.
- Every route sends a Content-Security-Policy and security headers from `apps/web/next.config.ts`: same-origin scripts (plus Google Tag Manager when GA is on, and `static.cloudflareinsights.com` when the Cloudflare beacon is on), connect/img limited to self (plus the hosts of whichever analytics is on; `/tools/breached-password-checker` alone also allows `api.pwnedpasswords.com`), `object-src 'none'`, `base-uri 'none'`, `form-action 'self'`, `frame-ancestors 'none'`, `X-Frame-Options: DENY`, nosniff, a Permissions-Policy. Share-holding paths (the set analytics skips: `/notes/[id]`, `/secrets/[id]`, `/files/[id]`, `/request/[id]` and inbox, `/chat`, `/links`, `/notepad`, `/share-target`) get the same policy without the analytics hosts. `'unsafe-inline'` remains in `script-src` because the App Router's inline bootstrap has no nonces.
- No ad network is integrated and no ad unit is rendered; there is no `ads.txt`. `apps/web/public/.well-known/security.txt` (RFC 9116) points vulnerability reports to `admin@protectedshare.me` and the disclosure section of `/security`.
- Theme follows `localStorage` or the system color scheme. That is a preference, not an account.

## Product Principles

1. The job is getting a secret from one person to another without making either of them create an account.
2. Plaintext stays in the browser. The server may store ciphertext, a verifier hash (v2 auth hash or v1 password proof) and the metadata needed to enforce limits, and future work has to say so.
3. Notes, EnvShare, file drops, secret requests, the notepad, and chat stay on that rule. A feature that needs the server to read the contents does not belong.
4. Expiry, burn-after-read, and read limits count only when the database row is actually deleted.
5. Published claims have to match what the code stores and sends.
